# WordCore 2 — The Plan

A from-scratch remake of WordCore: a small, fast CMS written in **Lua**, shipped as **one program** that runs on your own PC, on cheap cPanel hosting, on a VPS, or exported as a static site to GitHub Pages.

This document is the single source of truth for what we're building and in what order. Nothing here is code yet. Decisions marked **(open)** still need an answer.

---

## 1. Why a remake

The old PHP WordCore (`MightyX3N-Patrick/WordCore` + `WordCore-Repo`) works, but:

- There's no shared front-end layout. Pages, Blog, Docs and Forum each print their own full HTML page, so themes can't style the whole site.
- That's why every theme needed a companion addon (Ink & Page "engine", Slate "loader"), and themes only covered some addons.
- Things every site needs (pages, roles, front-end login) were addons, so code everywhere checked `class_exists(...)`.
- Every admin screen was hand-built, so ~9,000 lines were mostly the same patterns repeated.
- Security gaps: no-roles = every logged-in user is an admin, `admin/admin` default login, no session ID refresh or rate limiting, open redirect in front-end login, `data/` in the web root, Snippets ran stored PHP through `eval`.

We keep the good idea — **upload and go, no database server, addons and themes from a repo** — and rebuild everything else.

---

## 2. Principles

1. **Small core, everything else is an addon.** If most sites don't need it, it's not in the core.
2. **Content is always Markdown + shortcodes.** Whatever editor wrote it. Removing an addon never breaks content.
3. **Addons are sandboxed.** They get only the API we give them and only the permissions the site owner approved.
4. **One site folder, any machine.** The site is a folder. The WordCore program is swapped per platform. Moving hosts = copying the folder.
5. **Never hardcode the site's address.** It works at `localhost:8080`, through a tunnel, behind a proxy, at a subfolder, or at a real domain.
6. **Secure by default.** No default passwords, data outside the web root, rate limiting, CSRF everywhere, logins encrypted.
7. **Tested like a real user.** Headless Lua tests plus browser tests that click through setup, admin and front end before anything counts as done.

## 3. How it runs

One program, `wordcore` (`wordcore.exe` on Windows): a static Lua runtime with the native pieces we need built in. No Lua install, no libraries, no PHP, no nginx.

| Mode | Where | How |
|---|---|---|
| **Local server** | Your PC (Windows / macOS / Linux) | Double-click or `wordcore serve`. Runs at `http://localhost:8080`. Build the site here. |
| **Shared via tunnel** | Your PC + playit.gg (or any tunnel) | Same local server. With playit premium + domain, testers get a normal address with no port. Preview lock keeps it private. |
| **CGI** | cPanel / shared hosting | `.htaccess` sends every request to the Linux `wordcore` program. Lua starts in ~1 ms, so one process per request is fine. |
| **Server** | VPS / own server | `wordcore serve` as a service. Optional built-in HTTPS (Let's Encrypt), or behind nginx/Caddy/Cloudflare. |
| **Static export** | GitHub Pages, any file host | `wordcore build --static` renders every page to HTML. No server needed. |

**Risk:** some cPanel hosts block uploaded binaries or CGI. We test this on a real host in Phase 0, before building on top. Fallback for those hosts is static export or a VPS.

### Built into the program (native, C)

- Lua runtime: **Lua 5.5** (decided). Newest official Lua (5.5.0 Dec 2025, 5.5.1 since): `global` declarations catch typos in core and addon code, incremental major GC and compact arrays cut memory, and `_ENV` keeps sandboxing clean. Plain C, so it cross-compiles easily. LuaJIT was the alternative (faster, GMod-style Lua 5.1) but is harder to sandbox and build for ARM/macOS, and speed isn't the bottleneck for a CMS.
- SQLite (database)
- zlib + zip (install addons, build packages)
- Crypto: Argon2id password hashing, secure random, SHA-256, Ed25519 (signatures), encryption for saved logins
- TLS (HTTPS client for repo/GitHub/cPanel API; HTTPS server for VPS mode)
- libssh2 (SSH/SFTP publishing to a VPS)
- Socket/event loop for server mode (coroutine-based, non-blocking)
- Image resize + WebP encode (media optimisation)

Everything else is Lua.

### Build targets

`linux-x86_64` (hosting + VPS), `linux-arm64` (Pi, ARM VPS), `windows-x64`, `macos-arm64`, `macos-x64`. Linux builds are fully static (musl) so they run on any host.

## 4. The site folder

```
my-site/
├── wordcore(.exe)        # the program (per platform, not part of the "site")
├── .htaccess             # only in CGI mode, generated
├── public/               # the only folder the web server may serve directly
│   └── (theme + addon assets, media variants, generated by WordCore)
└── site/                 # everything else — never web-reachable
    ├── site.db           # SQLite: content, users, settings, addon data
    ├── media/            # original uploads
    ├── addons/           # installed addons
    ├── themes/           # installed themes
    ├── backups/          # automatic daily backups of site.db
    └── config.json       # mode, address, proxy trust, etc.
```

Saved host logins are **not** in this folder. They live encrypted in the user's OS config folder (e.g. `%APPDATA%\WordCore\` / `~/.config/wordcore/`) and never go into packages, backups or Git.

## 5. Core (what ships in the box)

### Platform
- HTTP layer for both server mode and CGI (same request/response API)
- Router with named routes, URL building that respects the site's real address and subfolder
- Proxy/tunnel awareness: `X-Forwarded-*` only when "trust proxy headers" is on
- Sessions (stored in SQLite, works in CGI), cookie security flags, session ID refresh on login
- CSRF on every form, rate limiting on login and forms
- Settings store, key/value store, migrations for core and addons
- Scheduled jobs (runs in server mode; in CGI mode on the next request or via cron)
- Logging and an error page that never leaks internals publicly

### People
- Users, roles and capabilities (no longer an addon)
- Owner account created in setup — no default login
- Optional 2-step login (TOTP)
- Front-end accounts (log in / register / reset) that addons like Forum reuse
- Password reset email (SMTP settings in core)

### Content
- **Pages** with nested slugs, drafts, scheduling, revisions, per-page access (everyone / logged in / roles)
- **Menus** builder
- **Media library**: uploads, MIME checks, optimised variants (resized WebP), alt text
- **Markdown**: CommonMark + tables, rendered by the core
- **Shortcodes**: `[name attr="x"]…[/name]`, registered by addons. Unknown shortcodes render as nothing for visitors, stay visible in the editor, and show a warning in the admin.
- **Editor slot**: the core Markdown editor (write / split / preview, toolbar, media picker, shortcode inserter). Any addon can replace it everywhere (Block Editor).

### Themes (one package, styles everything)
- A theme = `theme.json` + layouts + partials + assets + settings
- **One layout system**: every page from every addon renders inside the active theme's layout. Addons provide content and named templates; themes may override any of them.
- Regions/slots (header, nav, sidebar, footer…) that addons can add widgets to
- Theme settings (colours, fonts, logo) through the admin UI kit
- Template language: sandboxed Lua templates (etlua-style), auto-escaping by default
- No more "theme + loader addon"

### Admin
- Shell: sidebar, dashboard, site status strip (mode, public address, preview lock)
- **Admin UI kit**: addons describe screens in Lua (settings forms, list/edit screens, actions, dashboard cards) and get consistent UI for free
- Site health checks (passwords, data folder exposure, HTTPS, missing shortcode renderers, updates)

### Addons, themes, repos
- Install from repo, from `.zip`, or a folder
- Dependencies, minimum core version, update checks (core + addons + themes)
- Permission review screen on install (what it can / can't do)
- Repos: official one (`https://wordcore.space/repo/`) recommended in setup, extra repos allowed but marked unofficial
- The old Updater addon is gone — updates are core

### Publish & share (core)
- **Preview lock**: whole site behind invites / password, blocks search engines
- **Public address** detection + HTTPS mode (by tunnel/proxy, built-in Let's Encrypt, off). Built-in HTTPS (automatic Let's Encrypt certificates) is needed for HTTPS tunnels that pass encrypted traffic straight through (playit premium does this), so no Caddy/nginx is needed in front.
- **Export package** per target: cPanel (Linux program + `.htaccess`), VPS (program + service file), backup-only
- **Pairing — the main way to publish.** Most people never know their cPanel login (most hosts log you in to cPanel from their customer area), so publishing must not depend on it.
  1. *First install, once:* download the host package (zip), upload it in cPanel File Manager (or any file manager / FTP) and extract it. Visit the domain; the live site runs a short setup (owner account).
  2. *Pair:* in the live site's admin, "Pair with a PC" shows a short one-time code (expires in 10 minutes). Enter it in WordCore on the PC. The two exchange Ed25519 keys.
  3. *Publish / pull:* the PC sends signed update bundles to the live WordCore over HTTPS; the live site checks the signature, backs itself up, then applies. Pull works the same way in reverse.
  - Works on any host where WordCore runs (cPanel, Plesk, DirectAdmin, FTP-only hosts, VPS). No hosting passwords stored anywhere — only a pairing key, revocable from either side.
  - Security: the receiving endpoint is off until paired, accepts only requests signed by a paired PC (with timestamps/nonces against replay), is rate limited, logs every publish, and can be limited to "content only" or "content + addons/themes".
- **Advanced connections** (encrypted, for people who want WordCore to do the first install too, or run a VPS). The Add a host screen explains where to find each detail without a password (e.g. cPanel shows the username under *General Information*; tokens are under *Security → Manage API Tokens*):
  - cPanel — host, username, **API token** (UAPI over HTTPS), FTP/SFTP fallback
  - VPS — host, port (not always 22 — some hosts use another port), user, **SSH key** (generated by WordCore or existing), host fingerprint confirmation, optional service setup
  - FTP/SFTP — any host, upload only
  - GitHub — device-flow sign-in or fine-grained token; push **static site** (Pages) or **site source** (backup + history); writes `CNAME`
- **Backup before overwrite** of the live site, **pull live site to this PC**
- Small-host options: size estimate vs host quota (cPanel reports it), upload optimised images only, leave backups/revisions/unused media local, "slim" dynamic package
- **Static export**: `wordcore build --static` (also used by GitHub publishing and the future Actions addon)

## 6. Static mode

Every addon declares how it behaves in a static build:

- `full` — works as-is (Pages, Blog, Docs, Media, SEO)
- `fallback` — offers replacements the owner picks per site:
  - Comments → giscus (GitHub Discussions), Disqus, Cusdis, off
  - Contact form → Formspree, email link, hidden
  - Analytics → GoatCounter, off
  - Search → built-in index generated at export, searched in the browser
- `none` — not possible statically (Forum, logins, preview lock); the admin says so clearly

## 7. The addon sandbox

- Each addon runs in its own Lua environment. No `io`, `os`, `require`, `load` of bytecode, `debug`, `string.dump`, raw sockets.
- It receives a `wc` API object scoped to it: its own tables/KV namespace, its own folder, routes under paths it declared, hooks, admin UI kit, shortcodes, mailer (if permitted), HTTP client (if permitted, to declared hosts only), and — only with the `process` permission, which the owner approves separately and which is shown as high-risk — the ability to download a named, checksummed helper program and start/stop it (e.g. the playit agent). Never a shell.
- CPU and memory limits per request (instruction hook + allocator limit) so a broken addon can't take the site down.
- Permissions are declared in the manifest and approved at install; new permissions on update ask again.
- Manifests are data (JSON), never executed.

Draft manifest:

```json
{
  "id": "forum",
  "name": "Forum",
  "version": "2.0.0",
  "core": ">=1.0",
  "requires": { "media": "core" },
  "permissions": ["data", "routes:/forum", "accounts", "mail"],
  "shortcodes": ["forum"],
  "static": "none"
}
```

### playit Sharing addon

Share a site running on your PC through [playit.gg](https://playit.gg) without installing or configuring anything by hand. Publish & share → **Share with playit**:

1. **Get the agent** — WordCore downloads the official playit agent for this OS from playit's GitHub releases and checks its checksum. (The agent is open source under a BSD-2 licence; its notice is shown in the addon and kept with the download.)
2. **Link your account** — uses the agent's own claim flow (`claim generate` → claim URL → `claim exchange`): WordCore opens playit's approval page, you click approve, the agent gets its secret key. No password is ever typed into WordCore; the key is stored encrypted outside the site folder.
3. **Create the tunnel** — automatically, through the same API the agent uses:
   - *Free plan:* a TCP tunnel to the local server → an `http://name.joinmc.link:12345`-style address.
   - *Premium:* an HTTPS tunnel on your domain (a `.playit.plus` one or your own via CNAME) → WordCore's built-in HTTPS gets the certificate, so there's no Caddy step.
   WordCore detects which plan you have and says plainly what you'll get.
4. **Run it** — the agent starts and stops with the site; the dashboard status strip shows the public address; trust-proxy is turned on only when the tunnel type needs it; the preview lock is offered right there.

Risks and fallbacks:
- playit's tunnel-creation API isn't a documented public API (it's what their agent uses), so it can change. Linking uses their official CLI; if creating the tunnel fails, the addon shows the exact settings to enter on playit.gg instead.
- On the free TCP tunnel all visitors appear as `127.0.0.1` (the agent connects locally) — fine for previews, noted in the UI.
- Needs the core's `process` permission (above).

## 9. Repository layout & branches

**This repo (`MightyX3N/WordCore`)**

```
WordCore/
├── PLAN.md          # this file
├── runtime/         # the native program: Lua + C libraries, build scripts per platform
├── core/            # the Lua core (platform, people, content, themes, admin, publish)
├── addons/          # official addon source
├── themes/          # official theme source
├── tools/           # build, package, release, repo-index builder
├── tests/           # unit, integration, browser end-to-end
├── docs/            # developer + user docs (addon API, theme format, hosting guides)
├── registry/        # community addon listings for the official repo
└── design/          # admin design previews and notes
```

**Decided: one GitHub Pages site from a build-output branch.**

GitHub Pages serves one site per repo, so the website and the addon repo share it:

| Address | What |
|---|---|
| `https://wordcore.space/` | The WordCore website (and later the docs) |
| `https://wordcore.space/repo/` | The official addon & theme repository (`index.json` + zips) — the default repo URL in setup |

- Official addon **source** lives on `main` in `addons/` and `themes/`, next to the core, so changes to the API and the addons that use it land together and are tested together.
- A release script builds the website, zips each addon and theme, computes checksums, signs official packages, and writes everything into an orphan branch **`pages`** that contains only built output (website at the root, repository under `/repo/`, plus `CNAME` = `wordcore.space`). GitHub Pages serves that branch.
- Community addons stay in their authors' repos. They get listed by a PR to `registry/` on `main`; the build pulls their release zip, checks it, and includes it in the index.
- Benefits: `main` history stays free of zip files, the `pages` branch is always reproducible from source, and there's one place to contribute.
- `repo.wordcore.space` isn't needed anymore.

## 12. Licence

Decided: **GPLv3** for everything that comes from WordCore (program, core, official addons and themes, tools), plus the **[WordCore Addon and Theme Exception](LICENSE-EXCEPTION.md)**: independent addons and themes that only use the WordCore interfaces can use any licence, including closed source. Third-party libraries in the program keep their own licences. Sites and content made with WordCore aren't covered at all.

## 13. Package trust

Decided: **checksums for everything, signatures for official packages.**

- Every addon and theme in any repo index has a **SHA-256 checksum**. WordCore checks it after download and refuses a mismatch.
- **Official** packages (and core updates) are also **signed with Ed25519**. The public key is built into the `wordcore` program; the private key never goes in the repo (kept offline, or as a GitHub Actions secret for the release script) and is backed up.
- Only packages with a valid official signature are shown as **Official**. Everything else is shown as **Community** (official repo) or **Unofficial** (other repos).
- A hacked repo or website can't push a fake "official" update: without the private key the signature fails and sites refuse it.
- Key rotation: the program can carry the next public key ahead of time, so a lost or leaked key can be replaced with a core update.
